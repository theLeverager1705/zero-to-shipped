In one paragraph. Candidates come from IDF-weighted retrieval over rare name and address keys inside each country, computed as chunked sparse-matrix products so the whole corpus fits on one laptop. A two-stage LightGBM model scores each candidate pair: stage 1 uses 26 pairwise features; stage 2 adds 12 group-context features that compare each candidate with the entity's other candidates, because the true matches of one business resemble each other. A learned pre-filter shrinks the candidate set from 30 to about 3.8 per entity at no measurable cost, and a decision rule tuned directly for macro F0.5 turns probabilities into match lists.

1. Methodology

1.1 Problem and metric

For every Source 1 business, return all Source 2 / Source 3 records that describe the same real-world business. Scoring is macro F0.5 per Source 1 entity, with singletons included (a singleton scores 1 only for an empty prediction). F0.5 weights precision above recall, so the pipeline is tuned to avoid wrong merges.

1.2 What the data told us

  • Scale. 2.21M training and 1.73M test Source 1 entities, each split with about 10M Source 2+3 records. All-pairs comparison is impossible, so blocking has to use inverted indexes.
  • Labels. 5.6% of training entities are singletons; the rest have 1–11 matches (mean 3.7). In a 5,000-entity sample, all 17,362 true pairs share the country label, so country is a safe partition key.
  • Noise. Source 2 names are often written in native script (Bengali, Devanagari); unrelated trade/DBA names appear at the same address (Syndrex ↔ Straight Edge Pub, both at 515 Monroe Ave); injected diacritics (Cáble, Prívate); character swaps (Co1onial); word-order changes; legal-suffix churn (Pvt Ltd / Private Limited); abbreviated or reordered addresses; perturbed street numbers (26 vs 26/6).
  • Consequence: the address is as important as the name, and name-only matching fails.
  • Up to 349 lines per file contain a literal ", so files are read with quote handling disabled (QUOTE_NONE; every line has exactly 4 tab-separated fields).

1.4 Training and validation protocol

  • Hold-out by hash. About 10% of training Source 1 entities (CRC32 of the id mod 10 = 0) are excluded from training altogether and used only for end-to-end checks of the full pipeline.
  • Training sample. 300,000 Source 1 entities sampled from the rest (seed 42), blocked against the full training Source 2/3 corpus so candidate lists look exactly like test-time lists. This produced 8.99M labelled candidate pairs.
  • Entity-level split of that sample: 80% fit / 10% tune (early stopping and every rule or cutoff choice) / 10% report (never used for any decision; all reported scores come from here).
  • Out-of-fold stage 1. Within fit, two folds produce out-of-fold stage-1 probabilities, so stage 2 learns from probabilities of the same quality it sees at inference.
  • Fully deterministic: fixed seeds, LightGBM deterministic=True, murmur3 key hashing.

2. Candidate Generation / Blocking Strategy

2.1 Normalization

  • NFKD accent stripping (Cáble → cable), lowercase, apostrophes removed, all other punctuation to spaces.
  • Generic abbreviation expansion applied identically to every record: street types (rd → road, blvd, hwy ...), units (ste, apt, fl), directions (n, ne ...), Indian address words (ngr → nagar, opp, nr) and legal forms (pvt → private, ltd → limited, corp, inc).
  • Core name: the normalized name minus legal forms and function words (private, limited, llc, gmbh, sarl, sas, the, and, de, la ...), so Pvt Ltd / Private Limited churn disappears.
  • Derived fields: sorted unique address numbers, first address number (usually the street number), core-name token count, and the share of non-ASCII characters in the raw name (native-script detector).

2.2 Step 1: IDF-weighted rare-key retrieval

  • Keys. Core-name tokens (length > 1), core-name bigrams, address tokens (length > 1, or any number), and address bigrams, prefixed by type and hashed into 224 buckets (scikit-learn HashingVectorizer, binary, no vocabulary in memory).
  • Rare keys only. Keys occurring in more than 1,000 Source 2/3 records of the partition are dropped as non-discriminative.
  • Score. For Source 1 record q and Source 2/3 record c in the same country, with N the partition size and df(k) the key's document frequency:
score(q, c) = Σk ∈ Kname(q) ∩ Kname(c) idf(k)  +  Σk ∈ Kaddr(q) ∩ Kaddr(c) idf(k),    idf(k) = log(1 + N / df(k)) if df(k) ≤ 1000, else 0
  • Computation. For each country, Source 2/3 is indexed as a sparse key × record matrix; Source 1 rows are IDF-weighted query vectors. Scores for 5,000 Source 1 rows at a time are one sparse matrix product (name and address separately, then summed), followed by a vectorised top-K per row. The name and address parts of the score are kept and reused as features.
  • Country as an open set. Partitions are whatever labels appear in Source 1, so France (absent from training) needs no special handling. Country is never one-hot encoded or used as a model feature.
  • Why addresses: address keys recover true matches whose name is in a native script or is an unrelated trade name, where the name shares nothing with Source 1.

2.4 Step 2: learned pre-filter

The stage-1 model scores all 30 retrieved pairs, and only pairs with p1 ≥ 0.1 stay candidates. The cutoff is the largest value in {0, 0.001, 0.003, 0.01, 0.02, 0.05, 0.1} whose tune-split macro F0.5 is within 0.0001 of using no cutoff. The final (stage-2) model scores only these pairs, and they are exactly candidate_pairs.tsv; matches are always a subset.

3. Model Architecture and Feature Engineering

3.1 Stage-1 pair features (26)

All string similarities are computed with rapidfuzz.process.cpdist over whole arrays of pairs (C++, multithreaded), not per-pair Python calls, because the test set has tens of millions of pairs.

GroupFeatures

3.2 Stage-2 group-context features (+12)

True matches of one business resemble each other, so each candidate is judged against its entity's other candidates. The reference is the entity's best other candidate by p1.

GroupFeatures
Own position (3)Stage-1 probability p1; its rank within the entity; gap to the entity's best p1
Competition (4)Max and sum of the other candidates' p1; sum of other same-source candidates' p1; number of candidates with p1 ≥ 0.5
Reference (5)Reference's p1; same-source flag; name, address and address-number token-set similarity between this candidate and the reference

Example: a Source 2 record with an unrelated trade name gets little support from stage 1, but if it shares the address and numbers of a high-confidence candidate, stage 2 recovers it.

3.4 Decision rule (tuned for macro F0.5)

Two rule families are grid-searched on the tune split for each stage, and the (stage, rule) with the best tune score is kept:

  • Threshold rule: keep every candidate with p ≥ tall, plus the entity's single best candidate if p ≥ ttop. Only 5.6% of entities are singletons and an empty prediction scores 0 for everyone else, so a lower bar for the top candidate pays off.
  • Expected-F0.5 rule: per entity, with candidates sorted by p, predict the top j that maximizes EF(j) = 1.25 · Σi≤j pi / (j + 0.25 · (Σi pi + c)), where c estimates true matches that blocking never retrieved; predict nothing when s · Πi(1 − pi) (an estimate that the entity is a singleton) is larger.

Chosen: stage 2 with the threshold rule, tall = 0.725, ttop = 0.56, applied to the pre-filtered candidates.

4.2 Error analysis (report split, 30,057 entities)

  • Where recall is lost. Of 103,940 true pairs, 8,965 (8.6%) never reach the top-30 candidates and 6,266 (6.0%) are retrieved but rejected by the model. There are 1,837 false positives; 1,521 of 1,673 singletons are correctly left empty.
  • Share of lost F0.5: 69% partial recall on entities with matches, 24% entities with matches that get an empty prediction, 7% singletons given a false match.
  • False positives: near-identical distractors with the same name at a slightly different number (1572 vs 1582 Hardee Street, door 16-5-1 vs 16-5-3); a different business at the same address; one-character name changes (LFZ Foods vs LZ Foods) at an identical address.
  • False negatives: candidates with an empty address; true matches with an unrelated trade name or a name in Kannada or Devanagari script; heavy typos (CHENNAI PRTEDCTON); street numbers that differ between sources (1557 vs 1330 Bunce Road).

4.3 Compliance

  • Only the provided data is used: no geocoding, business registries, external APIs, web data or augmentation. The abbreviation and legal-form lists are short, generic, hand-written rules.
  • Dependencies are permissively licensed: LightGBM and rapidfuzz (MIT); pandas, NumPy, SciPy and scikit-learn (BSD; scikit-learn is used only for feature hashing). No GPL code. Model size is a few MB, far below 8B parameters.
  • candidate_pairs.tsv is exactly the set the final model scored, and matches are a subset of it.

4.4 Reproducibility and efficiency

  • python src/main.py train then python src/main.py predict reproduce the models and both output files; utils/validate_submission.py is the official validator, unchanged. All randomness is seeded.
  • Runs on one laptop (Windows 11, 14 cores, 31 GB RAM): training 31 min; test prediction 58 min (blocking 12 min, scoring 39 min over 51.9M retrieved pairs).
  • Memory-conscious engineering: sources are read and normalized in 1M-row chunks; each country's index is freed before the next is built; features are computed in ~3M-pair chunks that never split an entity's candidates (the gap and group features are per entity).
  • Output files are written with LF line endings and no quoting, since the official scorer strips only \n.

4.5 Limitations and next steps

  • Blocking recall is the main ceiling: 8.6% of true pairs are never retrieved. Transliteration-aware keys for native-script names and character n-gram keys for heavy typos are the most promising additions.
  • France is unseen in training. Normalization already drops common French legal forms and articles (SARL, SAS, EURL, de, la), and the features are language-agnostic, but the model and thresholds are calibrated on US and India data only.
  • Distractor records with a near-identical address need finer number handling, for example comparing structured door and unit numbers instead of token sets.
